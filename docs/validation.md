# Validation record

Tests exercise actual SQLite, certificate validation, generated stubs and child processes. No mock database, mocked service or fabricated successful ACK supplies a recovery result.

The independent large-list finding has a dedicated real-RPC red/green regression in `tests/test_listing.py`. Before the fix, 1,025 valid registrations with 64-character tenant/device names and 4,096-byte config payloads caused a 4,305,000-byte listing to exceed the default 4,194,304-byte client limit (`evidence/red-pagination.log`). After the fix, the same fixture traverses ten 100-device pages plus a final 25-device page, with a maximum response of 430,722 bytes. The real CLI, using 37-device pages and unchanged receive limits, returns all 1,025 IDs exactly once. The test also rejects invalid page sizes, malformed/tampered/foreign cursors and legacy empty requests, and resumes the same signed cursor after a server restart. It checks a second tenant with a colliding device ID. `evidence/pagination-regression.json` records those results; the independent reviewer's original probe and report remain unchanged for their recheck.

Java tests catch effects duplicated after reopen, changed replays, gaps, partial batch commits, tenant/device authorization mistakes, regressing config versions, concurrent retries, revocation bypass, unsupported protocol/size inputs and unusable configuration. Python tests cover durable queue capacity, sequence reuse, ACK deletion bounds, local configuration conflicts and payload size. Async tests run concurrent writes through the dedicated SQLite worker and cancel a disconnected network agent, checking cleanup and preserved rows. The transport test uses real mTLS identities and deadlines. The full drill combines three independent agents, two tenants sharing a device name, actual TCP termination, full journals, agent/server SIGKILL and restart.

Initial test files preceded implementation. `red-java.log`, `red-python.log`, `red-agent.log` and `red-transport.log` show missing implementation/build failures: these are compilation/import/setup failures, not runtime regression proofs. Subsequent behavior-level failures provide stronger red/green evidence: `red-config-validation.log` shows unusable desired config was accepted, and `red-integer-overflow.log` catches numeric truncation bypassing the interval bound. Both now reject the request before changing desired state.

The first outage failed because `grpc.aio.write()` can raise `InvalidStateError` when the transport closes between frames. `red-agent-outage.log` retains the stack trace and intact journal summary. The sender now reads terminal RPC status and applies its retry policy without deleting queued rows. The original grpcio 1.76.0 runtime also encountered Core `INTERNAL`/`FD shutdown` reconnection behavior on process restart. After pinning grpcio/tools 1.84.1 and regenerating bindings, full recovery passed. This is an observed version comparison, not conclusive attribution to a specific upstream defect.

The ACK-loss harness originally reused a TLS session after discarding ciphertext, which breaks TLS record continuity (`TSI_DATA_CORRUPTED`). It now closes that session and replays on a fresh authenticated connection. `red-ack-loss-harness.log` distinguishes this test-harness correction from a production bug. Expected failed TLS-handshake diagnostics from rogue-certificate tests remain visible in verification stderr.

Recovery assertions verify: all three devices end with sequences 1–160 exactly once; queues drain; desired/applied v2 converges despite a one-hour device-clock offset; an old config ACK cannot regress v2; a lost ACK replays as one duplicate and one database row; conflicting content is rejected; revocation rejects another frame on an existing stream; device/tenant spoofing and unauthorized certificates fail. The process drill uses SIGKILL, not an in-process reset. Physical power failure is not tested.

The final microbenchmark measures 3,200 samples in 100 batches through one warmed mTLS stream, with one outstanding frame and SQLite WAL/FULL commits. It includes database commit and response latency, excluding setup and handshake. Raw timings are retained. This small local workload does not establish thousands-of-devices capacity or an SLO. Profiling, when run, is reported separately from throughput because instrumentation affects timings.

Additional contract tests cover an unknown additive protobuf field, the 64-active-stream admission limit, capacity release after cancellation, and actual operator CLI output under a second tenant's certificate. Strict JSON validation has its own retained failing test (`red-strict-json.log`): accepting Java parser extensions such as single quotes would strand Python agents that parse standard JSON.

JDK Flight Recorder was run against the Java process through restart/recovery and a separate benchmark using `RELAY_PROFILE=1 python -m scripts.experiment`. The summary and observed sample counts are in `evidence/profile/`; the raw JFR binary is excluded from this public package. It captured 43 execution samples, 10 CPU-load events and 4 GC events. The short recording includes startup/JIT and predates the final strict-JSON parser hardening; it is not a definitive steady-state bottleneck analysis. `observations.json` retains the top observed methods and this limitation. To reproduce into a fresh directory:

```bash
RELAY_PROFILE=1 .venv/bin/python -m scripts.experiment --runtime .runtime/new-profile --output evidence/new-profile
jfr summary .runtime/new-profile/server-1.jfr
```
